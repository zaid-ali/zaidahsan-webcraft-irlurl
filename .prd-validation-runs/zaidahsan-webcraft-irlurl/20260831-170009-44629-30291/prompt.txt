# PRD Validation Rules

Use these rules to review Web Craft PRD documents as isolated product specs. Judge the document in context. Do not treat keyword matches as automatic failures when surrounding context makes the use acceptable.

## Hard Rules

### R1 - Human-Readable And Understandable

The PRD should make sense as a human product document.

Pass when:
- The product purpose, audience, and experience are understandable.
- Sections are coherent and not repetitive.
- The document reads like a human-edited spec rather than unreviewed AI output.
- Negated quality requirements such as "no placeholder text" or "no AI-generated assets" are used as requirements, not as authorship claims.

Fail when:
- The document is confusing or incoherent.
- It jumps into unexplained technical details with no product context.
- It has obvious unfinished placeholders, hallucinated sections, or repeated copy/sections that make it hard to trust.
- It includes AI-authorship/meta language such as "generated by ChatGPT", "as an AI", or similar.

### R2 - Proper Markdown Formatting

The PRD should use readable, valid markdown structure.

Pass when:
- Headings, bullets, tables, and code blocks render correctly in GitHub/VS Code.
- Escaped table pipes such as `\|` are used correctly.
- Nested bullets are indented clearly enough to render as hierarchy.
- Minor style differences do not harm readability.

Fail when:
- Tables are broken or unreadable.
- Code fences are unbalanced.
- Bullets/headings are malformed enough to render as walls of text or lose intended hierarchy.
- Pseudo-nested bullets use inconsistent or insufficient indentation in a way that renders as a confusing flat list.
- Markdown structure would confuse a human reader or downstream agent.

### R3 - No Replica/Original-Site References

The PRD should not say or imply that the product is a replica of another site.

Fail when:
- It uses words like "replica", "replication", "clone", "source site", "target site", "reference site", or "original site" to frame the work.
- It compares the product to an original/source site.
- It mentions scope being cut, altered, omitted, or limited relative to an original/source site.
- It has an "Out of Scope", "Excluded", "Not Included", "Omitted", "Scope Out", or similar section that enumerates concrete product features, pages, content modules, interactions, widgets, routes, rendering modes, or requirements as left out/cut from the expected site experience, even if it does not explicitly say "original" or "replica".
- It uses scope-cut language such as "explicitly excluded", "beyond this scope", "not part of rendered output for this scope", "omitted", or "left out" around concrete UI/content/features in a way that reads like a catalog of source-site functionality that was not reproduced.
- It includes screenshot paths or captions with replica/original framing, such as `screenshots/replica-home.png`.

Pass when:
- "Original" is used only for product state, such as restoring an original palette/value/order.
- "Reference" is used for document structure, template naming, or internal process labels, such as "Reference 1 format", and does not refer to a product, source site, original site, visual target, screenshot, or comparison baseline.
- A brief product non-goal is clearly a normal product boundary, such as "native mobile app is out of scope" or "payment processing is out of scope", and does not read like a list/catalog of omitted source-site functionality.

### R4 - No Implementation References

The PRD should describe what to build, not how this specific submission was built.

Allowed:
- API route contracts when they are part of the product's user-facing or integration-facing surface, not when describing route-handler/source implementation internals.
- Generic product/frontend terms such as root layout, layout shell, page layout, client navigation, or routing/navigation behavior when they describe user-facing structure.
- High-level shared template, route pattern, and page-architecture descriptions when they explain product structure without naming concrete source files, framework-specific implementations, or code internals.
- Phrases such as "shared implementation path" or "common implementation pattern" only when the surrounding context clearly means related pages share one product template/pattern and does not name concrete source files, folders, components, route handlers, frameworks, or code internals.
- Product/UI component guidance for specific features, shared components, and repeated page elements, when "component" means a product/UI building block rather than a named source-code component or library implementation.
- References to `index.html` when used as ordinary index/home page terminology rather than as part of a repo/file-structure discussion.
- Top-level static HTML page filenames such as `about.html` or `info.html` when they are clearly used as product page inventory, route/page names, or URL surface rather than codebase structure.
- CSS properties, design tokens, measurements, and visual-state specifications when they describe the intended product appearance or behavior.
- Typography specifications such as font size, weight, line height, letter spacing/tracking including negative values, font smoothing, text transform, and responsive typography values when stated as product visual requirements rather than source-code implementation.
- Browser/platform API names such as `localStorage`, `sessionStorage`, `history.replaceState`, `replaceState`, `getBoundingClientRect`, `setInterval`, `Intl.DateTimeFormat`, `IntersectionObserver`, `MutationObserver`, `requestAnimationFrame`, or Web APIs generally, when used to describe required product behavior or browser capability, not code structure or call patterns.
- Semantic HTML and accessibility requirements such as use of `header`, `nav`, `main`, `section`, `footer`, ARIA labels, focus order, keyboard navigation, or WCAG/contrast requirements when stated as product/accessibility behavior rather than submitted-code structure.
- Product-facing code/editor terminology when the product itself exposes code, editors, APIs, diagrams, developer tools, or technical content to users.
- Product-facing source-code or repository links when the product itself is about code or repository browsing, and the links are part of the product experience rather than references to the submitted repo.
- Detailed asset usage specs, including where assets appear in the product and necessary asset-internal names such as GLB nodes/layers, animation clips, shader/material names, texture maps, or media variants, when needed to use included product assets correctly.
- References to root-level `/public` or `public/` assets when describing available product assets, asset inventory, or expected asset usage.

Fail when:
- It references concrete source files or folders such as `src/`, `components/`, `styles/`, `src/app/page.tsx`, etc. Do not treat top-level static HTML page filenames as failures when they are being used as product page/route names.
- It nests or presents `public/` assets under source folders, such as `src/public/` or a `public/assets/` entry inside a `src/` directory tree.
- It references package/config/build files such as `package.json`, `vite.config.ts`, `next.config.js`, `nuxt.config.ts`, `tsconfig.json`, `build.mjs`, etc.
- It includes build/run commands such as `npm run dev`, `pnpm build`, `yarn start`, or similar.
- It specifies or recommends particular frameworks, libraries, runtimes, build tools, packages, or tech stack choices, unless the named technology is part of the product's user-facing domain or content.
- It references framework-specific architecture/router implementations such as App Router, Pages Router, React Router, BrowserRouter, Next.js routing, Nuxt routing, framework-specific layout files such as `app/layout.tsx` or `pages/_app`, or framework-specific navigation APIs.
- It gives library-specific or package-specific implementation guidance for product features instead of describing the product behavior or UI requirement.
- It references CSS class names, `className`, or implementation-only selectors.
- It includes actual code-call snippets, assignments, or source-like instructions using browser APIs, such as `element.getBoundingClientRect()`, `window.innerHeight`, `style.opacity = ...`, `uTime += 0.005`, event-bus wiring, DOM mutation instructions, or API usage written as code rather than product/spec language.
- It references JSX/source syntax, concrete source files, current implementation element choices, event handlers, hidden inputs, or mounted DOM structure as submitted-code documentation rather than accessibility requirements.
- It treats HTML/CSS/JS details as instructions for how the submitted code is structured rather than as product-facing requirements.
- It has repo/codebase/file-structure sections.
- It references framework implementation APIs/config fields such as `next/image`, `Next.js Image`, `useHead()`, or `app.head`.
- It describes mocked backend/route-handler internals.
- It gives code-level instructions for loading, parsing, rendering, disposing, or wiring assets, such as loader setup, renderer factories, lifecycle cleanup, module exports, or source-file organization.
- It frames requirements as optional implementation possibilities, such as "if implemented", "could be implemented", or "future implementation", when that wording shifts the PRD from product requirements into implementation planning.
- It has sections like "Implementation Summary", "Implementation Details", "Technical Architecture", or "Current Implementation".

Evidence guidance:
- Do not cite broad section headings as failure evidence unless the heading itself explicitly frames the PRD as submitted-code documentation.
- Do not fail high-level shared-template, route-pattern, or page-architecture language by itself when it stays framework-neutral and product-facing.
- Do not fail generic "shared implementation path/pattern" language by itself when the surrounding context is page-template/product-structure guidance.
- Do not fail browser/platform API names by themselves when they are used as concise product/spec guidance; fail the surrounding line only when it becomes code-like, source-structural, or implementation-internal.
- Do not fail typography values such as `48px / 700 weight / -0.02em tracking` by themselves; fail only if they are tied to framework utilities, CSS class names, source files, or implementation instructions.
- Do not fail semantic HTML or accessibility requirements by themselves; fail them only when they are tied to concrete source/code structure or current implementation details.
- Do not fail asset names, asset locations under root-level `public/`, or asset-internal layer/node/material names by themselves; fail the surrounding line only when it gives code-level loading, wiring, lifecycle, or source-organization instructions.
- For R4 failures, cite the specific concrete file/folder/config/command/class/API/code-internal line that violates the rule.

### R5 - No Submission-Artifact References

The PRD should stand alone as an isolated product spec.

Fail when:
- It references submission/workflow artifacts such as `SETUP.md`, `features.json`, `site.toml`, `PRD.md` as a file, Web Craft, Codimango, validation pipeline/checks, required deliverables, walkthrough video, review site, or submission workflow language.

Pass when:
- It uses generic self-reference such as "this PRD", "the PRD", "this spec", or "this document" to describe scope, authority, or what the product requirements cover, without referencing `PRD.md` as a file or another companion/root PRD artifact.
- It uses negative quality wording such as "not a build log" or "not a submission note" to say the product should read as standalone.
- It uses general product/ops quality language such as "simple to review, host, and maintain" when not tied to submission reviewers, required deliverables, challenge workflow, or artifact validation.
- It discusses normal product form submission behavior.
- It discusses product validation or user-facing validation.
- It discusses visual artifacts as product output, not submission artifacts.

### R6 - Scaffold-Level PRD Structure

The PRD should follow the general structure produced by the Web Craft PRD scaffold so a reviewer or downstream agent can predict where to find product overview, global requirements, surface requirements, and acceptance checks.

The expected top-level structure is:
- Product Overview.
- Audience and Core Experience.
- Global Design System.
- Global Accessibility Requirements.
- Global Content and Data.
- Product Surfaces.
- Acceptance Criteria.

Pass when:
- The PRD has recognizable top-level sections covering the expected scaffold areas, even if headings are renamed or combined lightly.
- Product Surfaces, or an equivalent section, is the center of the document and describes user-facing pages, routes, screens, states, modes, sections, or modals.
- Acceptance Criteria, or an equivalent verification/checks section, is present and separate enough to be used for validation.
- Acceptance Criteria act as a compact verification layer rather than a second full copy of the Product Surfaces section.

Fail when:
- The PRD is mostly a flat list, implementation note, checklist, visual inventory, or page dump rather than a structured product spec.
- It lacks Product Surfaces, or an equivalent section that organizes requirements by user-facing page/screen/state/surface.
- It lacks Acceptance Criteria, or an equivalent verification/checks section.
- It is missing multiple expected scaffold areas, such as no audience/core-flow section and no global design/accessibility/content sections.
- It puts most requirements into unrelated headings that make the scaffold organization hard to recover.

Evidence guidance:
- Do not require exact section titles or exact numbering.
- Do not fail because two closely related scaffold areas are combined when the content remains easy to find, such as "Audience and User Flows" or "Global Design and Accessibility".
- Do not fail because a small/simple product has short global content or accessibility sections.
- Do not fail because extra sections are present when the scaffold's core organization is still intact; use W4 to surface non-standard sections.
- Cite missing or malformed section headings when possible; otherwise cite the nearest top-level structure that shows the issue.

## Warnings

### W1 - Run-On / Collapsed Structure Warning

Warn when lines or sections pack many independent thoughts/specifications into a single hard-to-scan line or paragraph. This is subjective and does not affect hard-rule pass count.

Also warn when:
- A section uses long flat bullet runs where parent bullets and nested sub-bullets would be much easier to scan.
- Repeated structured records with shared fields are written as large comma- or semicolon-separated text blocks instead of a table or nested list.
- Inline code formatting is overused so ordinary descriptive prose, brand mentions, names, table cells, or narrative content become visually noisy.

Do not warn for long lines that remain clear, such as a coherent table row or a necessary detailed asset spec. Do not warn for backticks around routes, asset paths, UI labels, exact required copy strings, button text, menu items, tokens, colors, dimensions, states, keyboard keys, aria labels, IDs, or exact values. In large inventory tables, do not require every human-readable name/title cell to be backticked when the table context already makes those values exact content.

### W2 - Screenshot References Warning

Warn when the PRD references screenshots, screenshot folders, or screenshot filenames. This used to be recommended but is being transitioned away from, so it is advisory only.

Screenshot references can also cause hard-rule failures when they include replica/original/submission framing.

### W3 - Section Content Placement Warning

Warn when content appears to be placed in the wrong scaffold section in a way that makes the PRD harder to scan, but does not break the overall structure enough to fail R6.

Examples that can warn:
- Acceptance checks are mixed into Product Surfaces instead of being grouped under Acceptance Criteria.
- Acceptance Criteria duplicate most Product Surface requirements, repeat full content inventories, or expand into a long user-story list instead of summarizing high-signal verification outcomes.
- Detailed per-page copy, asset inventories, or component behavior are placed only in Global Design System when they belong with a Product Surface.
- Screen-specific copy, tutorial text, review messages, end-state copy, modal body copy, section-local headings, or one-surface asset lists are collected in Global Content and Data instead of being documented with the route/page/state/surface where they appear.
- Global Content and Data contains a substantial "exact fixed copy" block, or similar, that inventories local screen/state text such as tutorial, review, pause, or end copy. This can warn even if the same copy is also repeated under Product Surfaces, because the global duplicate still makes the document harder to scan.
- Global typography, color, spacing, or accessibility rules are repeated inside many surfaces instead of being stated globally.
- Product surface details are split across distant sections, forcing the reader to match copy in one place, assets in another, and behavior in another.

Do not warn when:
- A section includes a small amount of cross-reference context that helps readability.
- Local page copy is included inside Product Surfaces.
- Reusable catalog/content data is placed in Global Content and Data.
- Global Content and Data contains repeated CTA labels, reusable prize/product/catalog datasets, shared navigation/footer/legal copy, formatting rules, or asset-to-content mappings reused across multiple surfaces.
- The product is small enough that combined sections remain easy to scan.

### W4 - Non-Standard Extra Sections Warning

Warn when the PRD includes top-level sections outside the expected scaffold areas or clear equivalents. Extra sections do not fail R6 by themselves, but they should be surfaced so the author can decide whether the content belongs under a standard section or whether the scaffold template should evolve.

Expected scaffold areas are:
- Product Overview.
- Audience and Core Experience.
- Global Design System.
- Global Accessibility Requirements.
- Global Content and Data.
- Product Surfaces.
- Acceptance Criteria.

Warn when:
- A top-level section is not one of the expected scaffold areas or an obvious renamed/combined equivalent.
- A separate section such as Implementation Guidance, Technical Architecture, Out of Scope, Assets, Responsive Behavior, Accessibility, Content, User Stories, Testing, Performance, SEO, Analytics, Risks, Future Work, Deployment, or Dependencies appears as its own top-level section instead of being integrated into the standard scaffold.
- The extra section may be valid product material, but the content likely belongs under a standard section.

For each warning, include:
- The extra section heading as evidence.
- A short suggestion for the closest standard section, such as moving asset details into Global Content and Data or relevant Product Surfaces, moving responsive rules into Global Design System or specific Product Surfaces, moving accessibility rules into Global Accessibility Requirements, or moving verification checks into Acceptance Criteria.

Do not warn when:
- The heading is a clear equivalent rename of a standard section.
- Two standard scaffold areas are combined into one clear top-level section.
- Additional headings are subsections inside a standard section rather than extra top-level sections.
- The section is required by the product itself as a user-facing surface and is placed under Product Surfaces.

## Judgment Guidance

- Read enough context to decide whether evidence is actually problematic.
- Prefer false-negative tolerance over false positives when the rule is subjective.
- A hard failure needs clear evidence and a short rationale.
- Provide exhaustive line numbers and exact quotes for every failure or warning when possible.
- Do not provide only representative examples. If a rule fails in multiple non-adjacent places, cite every distinct occurrence.
- Do not stop after finding enough evidence to justify a fail verdict. Continue scanning the full PRD for additional evidence for that same rule.
- If many adjacent lines form one continuous offending block, cite the first line of the block and explain the block range in the reason. If similar issues recur elsewhere, cite those occurrences separately.
- If the issue is borderline, use `confidence: "medium"` and explain why.
